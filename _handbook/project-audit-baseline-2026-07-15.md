## 3. 总体判断

小满已经具备相对完整的个人助手骨架：

- 前台 Agent Loop 与工具调用。
- 会话持久化和任务运行状态。
- 持久化 Workflow。
- 精确定时提醒。
- 分层记忆和 Akasha 经历索引。
- 主动数据源、注意力判断、Draft、反馈和 ActionPlan。
- Dashboard、QQ、微信等多渠道入口。
- MCP、Skill 与模型接入能力。

目前的主要问题不是缺少更多功能，而是部分跨模块边界没有真正闭合：

1. 外部渠道身份和主机操作权限缺少统一、不可绕过的执行边界。
2. Scheduler 的“已发送”语义、失败记录、取消和崩溃恢复不可信。
3. Workflow 能恢复流程状态，但外部副作用仍可能在重启后重复执行。
4. Attention Engine 的领域设计基本成立，但 provider、学习观察、执行器和状态确认仍存在旁路或断点。
5. Dashboard 对提醒、长会话、附件、运行状态和主动行为的呈现没有形成完整产品闭环。
6. 部分历史模块、旧面板和无消费者存储可能已经成为废代码，但删除前仍需运行时和数据证据。

长期治理原则仍是：**先封闭真实风险和错误语义，再补齐产品闭环，最后做分包与删除；每次只处理一个可独立验收的问题。**

### 3.1 当前迭代的范围裁剪

本文第 5 节记录的是完整审计池，不代表当前迭代要全部实施。现阶段只修复用户能够直接遇到、会阻断日常使用或会让系统给出错误结果的问题。

一个问题只有同时满足以下条件，才进入当前迭代：

1. 用户已经实际遇到，或可以用很短的路径稳定复现。
2. 影响聊天、文件、提醒、任务中断、渠道通信或主动协助等核心使用路径。
3. 可以在现有架构内完成边界清晰的修复，不要求先进行大规模迁库或重构。
4. 能写出面向产品结果的验收条件，而不只是“代码更优雅”。

以下事项本轮不主动开展：

- 全系统 ExecutionPrincipal/owner 字段迁移。
- 将 Scheduler 整体迁入 workflows.db。
- 重写 Workflow 状态机或追求通用 exactly-once 框架。
- Dashboard 远程部署与完整多租户鉴权体系。
- 数据库合并、migration 框架统一和 sidecar 全面治理。
- 全量目录重排、依赖倒置和历史模块清理。
- 没有当前故障证据的理论性能优化和安全加固。

例外是能够用很小修改阻断的直接安全问题，例如 QQ/微信只允许已配置账号、危险操作继续服从现有权限等级。这类问题不需要扩展成全系统权限重构。

## 4. 当前架构基线

### 4.1 主要运行链路

1. `main.py` 创建并启动应用运行时。
2. Bootstrap 负责配置读取、依赖装配、服务注册和生命周期管理。
3. 被动 Agent Loop 处理 Web、QQ、微信等渠道发起的普通对话。
4. Workflow Runtime 承接可恢复的多步骤任务、等待用户、审批和重试。
5. Scheduler 负责用户明确指定时间的提醒。
6. Proactive/Attention 链路汇总数据源和记忆，判断是否值得主动协助。
7. Dashboard API 与渠道适配器负责输入输出，不应拥有领域规则和基础设施编排职责。

### 4.2 Attention Engine 当前领域结构

Attention 已经包含以下概念：

- Signal：来自个人状态、主动数据源、MCP、待办和上下文的原始信号。
- Observation：可用于学习的模式或策略证据。
- Pattern：可更新、可失效的行为规律。
- Policy：确定性限制或经过治理的主动行为策略。
- Opportunity：时间窗口和主动协助机会。
- Capability：系统当前能够执行的通用能力。
- Candidate/Score：候选动作与效用、打扰成本、置信度评分。
- ActionPlan：被选中的动作计划及其状态。
- Execution/Feedback：执行结果和用户反馈。

领域方向是合理的，问题主要集中在运行时接线，而不是需要重新发明一套注意力算法。

### 4.3 数据职责基线

现有数据库和存储不能因为数量较多就直接合并或删除：

- `sessions.db`：会话、消息和聊天历史。
- `workflows.db`：Workflow、步骤和运行事件。
- `personal.db`：稳定个人事实、记忆治理、向量侧车和 Attention 领域数据。
- `memory2.db`：执行经验等记忆数据。
- `akasha.db`：完整经历的可检索、可追溯索引，可由源数据重建。
- `consolidation_writes.db`：记忆整理写入过程。
- `proactive.db`：主动投递或节拍诊断数据；不应成为 ActionPlan 的权威状态源。

数据职责可以继续收敛，但必须先确认生产读写者、数据迁移方式和重建策略。

## 5. 已确认问题清单

优先级含义：

- P0：存在高影响安全边界问题，应优先阻断，但仍需确认威胁前提。
- P1：会导致核心功能错误、数据状态不可信或明显产品失效。
- P2：架构耦合、数据治理和长期维护问题。
- P3：体验瑕疵、历史残留和低风险清理。

### 5.1 P0：外部渠道与主机副作用权限边界

#### 现象

- 当前确定性 Permission Hook 主要覆盖被动 Dashboard 路径。
- Background、外部渠道或其他运行来源可能没有经过同一权限判断。
- Shell、文件写入、消息发送等高副作用工具存在 always-on 注册路径。
- QQ/微信空 allowlist 可能表示允许所有发送者。
- Shell 和文件工具的 workspace 边界未形成统一强制约束。

#### 风险

未经确认的外部发送者可能诱导 Agent 读取或修改主机文件、执行命令，或者向其他人发送消息。模型“是否愿意调用工具”不能作为安全边界。

#### 正确方向

- 渠道适配器生成可信执行主体，模型和请求体不能伪造。
- 所有前台、后台、Workflow、Scheduler、Attention、MCP 和子任务共用统一 admission/permission 层。
- 外部渠道默认不能使用主机高风险工具；需要用户绑定和按操作审批。
- 空 allowlist 应 fail closed。
- 文件与命令操作统一限制到配置的工作区，并防止绝对路径、`..`、符号链接和 junction 逃逸。

#### 产品校准

小满是单用户个人助手，不应简单把每个聊天都当成互相隔离的“多租户”。正确模型是：

- 一个本机 owner。
- 多个经过授权的 owner 渠道身份可以共享个人长期记忆。
- 未绑定或公共渠道发送者只是外部 subject，不能自动获得 owner 权限。

### 5.2 P0 候选：Dashboard 管理接口保护不足

#### 现象

- Dashboard HTTP 管理路由主要依赖回环地址隔离。
- 只有聊天 WebSocket 有较明确的 Host/Origin 检查。
- MCP 管理接口可以接收 stdio command、环境和工作目录，并启动本机进程。

#### 风险前提

只有在远程绑定、错误反向代理、Host/Origin 绕过、DNS rebinding 或浏览器本地网络访问保护失效时，才可能升级为远程配置破坏或本机命令执行。

#### 结论

这是需要加固的高影响入口，但静态报告只证明了“危险组合存在”，没有证明默认纯回环部署已经可被远程利用。因此应先完成真实浏览器与部署条件验证，再决定完整鉴权方案；不应直接为了理论多用户场景重写整个 Dashboard。

### 5.3 P1：Scheduler 不能可信表示“已提醒”

#### 已确认缺陷

- Dashboard 创建提醒时写死 `dashboard:xiaoman-console`。
- 实际 Dashboard 会话使用动态 UUID，写死目标并不存在。
- Dashboard broker 要求目标会话当前有订阅者，离线或页面未挂载时会失败。
- 消息推送失败以返回值表达，而 Scheduler 没有可靠识别，仍增加 `run_count`。
- 一次性任务可能在失败后被删除；周期任务可能显示已执行但没有送达。
- 发送成功后、状态落盘前崩溃可能重复发送。
- 正在执行的周期任务被取消后，仍可能在结束阶段重新生成下一次执行。
- 只有创建、列表和删除，缺少修改、发送尝试、失败原因和重试状态。

#### 正确语义

- 明确指定时间的提醒继续走 Scheduler，不经过 Attention utility score。
- 创建时绑定可信发起会话或明确回复目标。
- 发送结果必须是 typed success/failure，不能用普通字符串混合表达。
- `run_count` 只统计确认成功的投递。
- 每次 occurrence 要有稳定 ID、执行状态、投递尝试和取消标记。
- 修改、取消、失败、重试和实际发送时间对用户可见。

#### 待决策项

“把 schedules.json 全部迁入 workflows.db”只是一个架构候选，不是修复上述问题的必要前提。应先写数据所有权和幂等设计决策，再选择独立 Scheduler Store 还是复用 Workflow Store，禁止为了修提醒顺手重写任务系统。

### 5.4 P1：Workflow 外部副作用可能重放，停止范围不完整

#### 保留的能力

现有 DAG、循环检测、依赖关系、等待用户、审批、重试和恢复机制有价值，不应重写。

#### 缺陷

- 重启时会将部分 RUNNING 步骤重新置为可执行状态。
- 如果外部副作用已经完成、但步骤完成状态还没落盘，恢复后可能再次执行。
- `/stop` 主要取消前台会话，未必能传播到 Workflow、子任务、Scheduler occurrence 和后台任务。
- 切换会话后，仍在运行的任务可能不可见或不可停止。

#### 正确方向

- 给外部副作用建立 durable operation/attempt ID 和幂等键。
- 执行前持久化意图，执行后持久化 receipt。
- 统一 owner/session/run 级取消注册表。
- 在 claim、执行副作用、提交状态、生成后继任务前检查取消。
- 所有运行事件通过统一查询暴露给 Dashboard 和渠道。

### 5.5 P1：Attention Engine 集成边界存在旁路和数据丢失

#### 缺陷

1. 某个 signal provider 抛错时，外层 gateway 可能退回原始 MCP alerts，绕过 Attention 的策略、评分和 ActionPlan。
2. 外部 ACK 可能先于 ActionPlan 完成；消息已送达时，计划仍可能停留在 `PROPOSED`。
3. MCP 的 pattern/policy observations 没有完整进入学习链路。
4. Personal provider 只转发部分 observation，policy observation 可能丢失。
5. 用户明确表达的 opportunity 仍可能受推断置信度阈值限制，也没有立即锁定为明确知识。
6. Observation ID 受数组顺序和可变 payload 影响，同一证据可能被重复计数。
7. MCP 未提供 event ID 时，同一 server 的同类事件可能碰撞覆盖。
8. 通用 `ActionExecutionService` 已存在，但运行时仍有 `message.notify` 特殊手工状态流。
9. 当前新增 Capability 并不等于自动获得可执行 handler。

#### 正确方向

- provider 逐个隔离；失败进入诊断或隔离区，不能退回旧通知旁路。
- Observation 使用来源稳定 ID 与语义 rule key，排序和展示字段不能改变身份。
- 明确表达立即进入明确知识治理；推断规则继续依赖多证据和置信度。
- 所有能力通过统一 handler registry 执行；没有 handler 时确定性失败。
- ActionPlan 状态迁移和 outbox 记录保持一致，重复 callback 只能形成一个逻辑动作。
- 反馈只更新与反馈相关的时机、内容或相关性维度。

#### 产品校准

Attention 不应退化为“已有通知发不发”的闸门。它应基于记忆、情绪、待办、机会窗口和能力生成候选动作，并在通知、内容推荐、建议处理待办、执行被授权工作流和保持安静之间选择。具体的“地铁”“健身”情形不能写死在核心代码中，应由通用 Signal、Observation、Pattern、Policy、Opportunity 和 Capability 表达。

### 5.6 P1：MCP 密钥可能绕过安全存储边界

#### 现状

MCP registry 使用 keyring 或引用的方向合理，但管理工具仍可能让模型直接接触原始环境变量值。通用 tool-chain、会话和 Akasha 来源又会持久化工具参数。

#### 风险

密钥可能进入日志、错误、工具过程、会话数据库或记忆索引。

#### 正确方向

- LLM 只接触 opaque secret handle。
- 可信 executor 在实际调用边界解析密钥。
- 日志、事件、tool-chain、会话持久化和 UI 序列化使用同一套 schema-aware redaction。
- 历史数据只能先做数量和字段级 dry-run，不能为了扫描而输出秘密值。

### 5.7 P1：聊天、附件与运行状态的产品闭环不完整

#### 长对话

- 当前默认读取 page 1、升序 100 条。
- 超过 100 条后重新打开，只显示最早的消息而不是最新对话。
- 正确方案是默认加载最新一页，按时间正序显示，并向上游标加载更早内容。

#### 运行状态

- 持久化的工具链和后台运行过程未完整呈现。
- 断线错过 terminal event 后，页面可能一直显示忙碌。
- 外部渠道发起的任务可能无法在 Web 中查看和中断。
- 正确方案是重连后同时对账持久化消息和 run terminal state。

#### 附件

- UI 宣称支持 PDF、Office、ZIP 等格式，但内置 `read_file` 不能解析二进制文档。
- MarkItDown 当前只是可选 MCP，不应在未安装或不健康时承诺支持。
- 附件索引部分存在于内存，重启后 ID 可能失效。
- 缺少会话删除、未发送失败和 retention 对应的生命周期清理。
- 应持久化附件 metadata，并根据健康 parser capability 动态展示支持格式。

#### 主动行为与任务页面

- 后端存在 pending Attention approval，但 UI 缺少完整入口。
- My Day、Task Center 缺少统一实时事件更新。
- 模型选择器表面像会话级切换，实际可能修改全局配置。

### 5.8 P2：架构与数据治理问题

- `core.attention` 依赖 personal 具体实现，存在领域层反向依赖。
- Attention provider、工具或服务在多个 bootstrap 位置注册，“单一装配根”不完整。
- Dashboard route 混合请求处理、配置写入、运行时重配置和基础设施调用。
- 边界 contracts 使用较多 `Any`，削弱模块契约。
- `personal.db` 的 migration version 可能被多个 store 共享，缺少命名空间。
- Workflow schema 有临时列探测，部分 sidecar 缺少外键或孤立数据清理。
- QQ 支持部分 Markdown 降级，微信主要为纯文本；统一 outbound parts 和渠道能力协商尚未完成。
- Focus/DND 与部分高优先级规则仍有硬编码，Attention UI 没有完整显示拒绝原因、窗口、分数和计划。

## 6. 不应直接照搬的原计划结论

以下方向需要单独设计决策，不能作为审计发现直接执行：

1. **不能把单用户个人助手机械改造成多租户系统。** 应区分本机 owner 与未授权外部 subject，同时允许 owner 在授权渠道间共享个人记忆。
2. **不能为了 Scheduler 正确性直接迁移全部数据到 workflows.db。** 可靠状态机和数据库归属是两个问题。
3. **不能重写已有 Workflow。** 应在现有状态机上补幂等、副作用 receipt 和取消传播。
4. **不能仅凭数据库数量多就合并或删除记忆存储。** Akasha、长期个人记忆、执行经验和整理记录职责不同。
5. **不能把 Dashboard 静态风险描述成默认环境已被远程攻破。** 必须验证绑定方式、代理、Host、Origin、PNA 和 DNS rebinding 前提。
6. **不能把健身、通勤、午休等具体场景写进核心分支。** 新场景应主要增加数据、规则实例或 MCP capability，而不是新增硬编码判断。
7. **不能整体恢复 Claude 的未完成 stash。** 只能在明确任务中逐文件参考，重新实现并独立验证。

## 7. 废代码与删除候选

### 7.1 高置信候选

`PersonalAutomationStore` 及以下表被报告为只有构造、关闭和 context 注入，没有生产 producer/consumer：

- `personal_events`
- `personal_operations`
- `personal_operation_audit`

1. 全仓定义与引用扫描。
2. Bootstrap/runtime registration 扫描。
3. 数据库仅做 schema、行数和孤立关系检查。
4. 确认没有外部插件或旧版本迁移依赖。
5. 明确由 Workflow event/audit 替代的路径。

确认后应删除实现、装配、专属测试和表，不保留无消费者兼容适配器。

### 7.2 条件候选

- 旧 Dashboard plugin panel runtime/compiler。
- Akasha/default-memory 技术配置面板。
- `frontend/dashboard/src/design/` 旧设计层。
- 重复 CSS、旧 types 和无消费者依赖。
- 无事件处理器的麦克风、桌面壳或伪按钮。
- 已失效 README 和 Handbook 内容。

删除门禁：必须先确认当前 registry、配置、路由、动态加载和外部插件没有消费者。如果仍有真实扩展用途，应保留清晰的通用扩展槽，而不是保留旧 UI 再加一层胶水。

- `memory2` 执行经验记忆。

## 8. 当前迭代：只修影响使用的问题

以下是当前唯一有效的实施队列。开始每项任务前先在当前基线复现；已经正常的功能只记录结果，不为了“可能有问题”而改代码。每项任务独立修改、独立验收，完成后再决定是否进入下一项。

### 当前任务 1：文档上传与解析

这是当前最高优先级，因为用户已经实际遇到“加号无反应、拖拽不识别、安装了解析能力但聊天不能使用”。

只解决以下产品结果：

- 点击加号能选择文件，拖拽文件能进入当前聊天。
- 前端只展示当前实际安装且健康的解析器所支持的格式。
- PDF、Word、Excel、PPT 等文件由统一附件入口交给当前可用的文档解析工具或 MCP。
- 解析结果进入当前会话，Agent 能引用文件内容继续回答。
- 解析器缺失、格式不支持、文件过大或解析失败时给出明确可操作提示。
- 附件与会话的关联不会因为一次页面刷新立即丢失。

本任务暂不扩展为通用文件资产管理系统，也不顺带重写 MCP、会话存储或全部附件 retention 机制。

产品验收：分别用加号和拖拽上传一个 PDF、Word、Excel、PPT；要求至少已声明支持的格式能被实际读取并回答文件内问题，未支持格式必须明确拒绝，不能假装解析成功。

### 当前任务 2：明确提醒可靠送达

修复审计已确认的真实错误：

- 不再发送到不存在的 `dashboard:xiaoman-console`。
- 失败投递不能增加成功次数。
- 一次性提醒发送失败后不能无痕删除。
- 用户至少能看到提醒的目标、计划时间、成功或失败状态及失败原因。
- 修改和取消按钮必须真实生效。

本任务不要求先把 Scheduler 迁入 workflows.db，也不要求一次解决所有分布式幂等理论问题。

产品验收：创建一个两分钟后的提醒，分别验证在线送达、目标页面关闭时的处理、修改、取消和失败状态；明确提醒不得经过 Attention 评分。

### 当前任务 3：聊天历史正确性

- 新建对话不能覆盖旧对话。
- 重新打开长对话时显示最新消息，而不是最早 100 条。
- 支持向上加载更早记录。
- 切换会话和刷新页面后，消息归属不能串线或消失。

产品验收：使用两个会话交替发送消息；构造超过 100 条的会话并重新打开，确认默认看到最新消息且可以加载旧消息。

### 当前任务 4：运行任务可见并可停止

- 正在运行的会话在对应聊天记录右侧显示运行标记。
- 切换到新会话后，旧会话任务仍可见，不会变成“看不见但继续运行”。
- 当前会话和历史会话中的运行任务都有可用的停止入口。
- 停止后界面、后端运行状态和会话记录保持一致。
- 断线或刷新后通过持久状态对账，不能一直卡在“思考中”。

本任务只修用户可见的运行管理，不在本轮建立覆盖所有 Workflow/Scheduler 的通用分布式取消框架。若当前停止机制无法触达某类实际运行，再针对该运行类型补齐。

### 当前任务 5：QQ/微信消息呈现与基础渠道保护

- QQ/微信不能直接显示 `**`、反引号等未渲染 Markdown 标记。
- 根据渠道能力输出富文本或干净的纯文本降级。
- 长消息分段、代码、列表和链接保持可读。
- 只允许配置中明确授权的账号使用个人助手。
- 删除文件、执行命令、安装软件和代发消息继续服从现有权限等级。

本任务不建立新的渠道平台，也不进行全系统 owner 数据迁移。

### 当前任务 6：主动协助链路中的确定性断路

Attention 是产品核心，但本轮只修会让现有功能直接失效的接线错误：

- 单个 provider 失败不能把未经治理的原始通知直接发送给用户。
- 已经产生的 pattern/policy observation 不能在适配层被静默丢弃。
- 用户明确表达的机会窗口不能继续按普通推断证据处理。
- 消息已经送达时，ActionPlan 不能仍显示为未执行。

稳定 ID、通用 Capability executor、依赖倒置和完整反馈学习框架留到后续，除非它们是修复以上具体故障的最小必要条件。

### 当前任务 7：小范围回归检查

只复查用户此前实际遇到过的路径：

- 新建聊天和聊天记录保存。
- 模型切换是否立即作用于后续新请求。
- 渠道配置保存和网关重启按钮。
- 权限等级选择与危险操作审批。
- Dashboard 页面刷新后当前状态是否恢复。

已经正常的功能不改代码，只记录通过结果。

### 后续待办，不进入当前迭代

- 全系统 ExecutionPrincipal 和 owner-scoped repository。
- Dashboard 完整远程鉴权、CSRF 和多用户会话。
- Scheduler 数据库迁移和通用 outbox 架构。
- Workflow exactly-once、全执行域统一取消。
- Attention 全能力注册表和依赖层重构。
- MCP 历史数据脱敏迁移。
- 数据库 migration/FK/orphan 全面治理。
- 分包重排、旧插件面板、PersonalAutomationStore 和其他废代码删除。
- UI 设计系统、重复 CSS、类型层和文档的全面整理。

这些内容继续保留在审计池中，等当前核心功能稳定后再按实际收益选择，不自动排入开发计划。

## 9. 产品级验收场景

### A. 长期对话与记忆

- 输入长期目标、作息、偏好、经历和执行经验。
- 验证短期语境、个人事实、完整经历、执行记忆和 Attention observation 各有唯一职责。
- 新会话能按需召回，而不是把所有记忆全量塞入上下文。
- My Day 和 Attention 实际消费相关记忆。
- 验证重复、冲突、版本、权限、过期和时间衰减。

### B. 明确提醒

- 从 Web、QQ 或微信创建“今天 15:00 提醒我汇报”。
- 必须直接进入 Scheduler，不经过 Attention 评分。
- 验证修改、取消、离线、失败、重试、重启、时区和投递记录。

### C. 通勤机会窗口

- 多次表达工作日通勤存在约 20 分钟空闲。
- 单次推断不应立即打扰，多证据后形成可失效规律，明确确认后锁定。
- 系统根据现有能力选择内容、资料预览、碎片待办或保持安静。
- 核心代码不得包含“地铁”专用分支。

### D. 健身 MCP

- 通过通用 MCP 接入训练、饮食、睡眠和恢复数据。
- provider 失败时保持安静并记录诊断，不把原始事件直接推送。
- 模型可以根据证据生成鼓励、恢复建议或“信息不足”。
- 核心不得写死 `nutrition_training_mismatch` 等特定领域分支。

### E. Focus 与 DND

- 普通主动动作被确定性限制时，UI 能显示具体阻断原因。
- 明确时间提醒按产品约定独立处理。
- 学习到的策略只能增加限制或要求审批，不能绕过安全规则。

### F. 多渠道并发

- Web、QQ、微信同时发送消息。
- 会话、运行、回复目标和取消互不串线。
- 经授权的 owner 渠道可以共享长期个人记忆。
- 未绑定发送者不能取得 owner 权限。
- 各渠道得到其支持的文本/Markdown/图片/文件格式。

### G. 复杂任务

- 覆盖 Agent、子任务、等待用户、审批、重试和重启。
- 在外部副作用完成后注入故障，确认恢复时不重复执行。
- 切换会话后任务仍可见。
- `/stop` 能传播到子任务和后台运行。

### H. 文件上传

- 加号与拖拽上传 PDF、Word、Excel、PPT。
- 重启后附件仍可恢复。
- parser 缺失或失败时给出可操作错误，而不是假装已解析。
- 会话删除和 retention 会清理文件与索引。

## 10. 每个任务的交付要求

每完成一个任务必须汇报：

1. 修改了哪些生产代码、测试和迁移，新增/删除行数分别是多少。
2. 删除项的定义、引用、runtime registration、数据读写、影响和替代路径。
3. 最小自动化测试结果和真实产品场景结果。
4. 对旧类名、旧路由、旧表、fallback、双写和双读的残留扫描。
5. 是否仍有双轨机制，不使用“基本完成”代替明确状态。
6. 当前服务是否运行、使用何种配置。
7. 未验证项及原因，不能用 mock 通过冒充真实 QQ、微信、OAuth 或第三方 MCP 验收。

## 11. 修改纪律

- 先复现或证明问题，再修改。
- 一次只处理一个可独立验收的主题。
- 不使用 `git reset --hard` 或 `git checkout --` 覆盖用户工作。
- 数据迁移前先停止 writer、备份并在副本 dry-run。
- 不读取或输出用户秘密、私人消息正文。
- 不为旧实现制造兼容 host、shim 或新的胶水层。
- 不因测试难写就保留无消费者代码。
- 不因新架构更漂亮就重写已经可靠的模块。
- 所有目录调整必须服务于清晰所有权和单向依赖。

## 12. 推荐的目标依赖方向

```text
UI / Channels
    -> Application Use Cases / Agent Tools / Workflows
        -> Domain Services
            -> Domain Models / Ports
                <- Infrastructure Implementations

Bootstrap
    -> 只负责依赖装配、注册和生命周期
```

关键边界：

- Channel 负责把不可信输入转换为带可信主体的请求。
- Permission/Admission 负责所有执行来源的确定性准入。
- Agent/Workflow/Scheduler/Attention 负责各自用例，不直接拥有 UI 或渠道规则。
- Attention Core 只依赖领域 Port，不依赖 Personal 或 Proactive 的具体实现。
- Route 不直接写配置、启动进程或编排领域状态。
- Infrastructure 不把秘密值和私人内容泄露到日志、事件和索引。

## 13. 下一步建议

下一项只处理“文档上传与解析”。先复现加号、拖拽、附件上传、解析器发现和对话引用的完整链路，再做最小修复并使用真实 PDF/Office 文件验收。完成并汇报后，才进入明确提醒或其他任务。不要从权限体系、数据库迁移、目录搬迁或 UI 全面改版开始。
