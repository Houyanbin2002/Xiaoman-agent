# 工程问题与改进记录

只记录具有复用价值的问题：会污染状态、误导评测、破坏数据治理，或可能在其他模块重复出现的问题。普通一次性报错不记录。

## 2026-08-23：同一偏好被跨标签重复写入

- **现象：** “旧项目 → Xiaoman 项目”被写成“旧项目 → Xiaoman → Xiaoman 项目”，产生无意义的中间版本。
- **根因：** LLM 抽取为 `project_context`，显式规则抽取为 `correction`；旧去重逻辑依赖候选标签，没有识别二者实际写入同一个 `active_project` 槽位。
- **方案：** 写库前按“来源消息 + 语义槽位”统一候选，与标签无关；同批次同槽位采用最后一个高权威候选，同值重复只增加证据。
- **验证：** 单元测试确认版本链只有两代；真实 AgentLoop 纠错用例 1/1 通过。
- **经验：** 记忆治理的身份应由稳定业务键决定，分类标签只用于描述和检索，不能作为写入唯一性依据。

## 2026-08-23：Judge 异常被误报为 Agent 失败

- **现象：** Agent 已正确完成任务，但 Judge 返回非 JSON 后，运行器将真实结果替换成 `status=error`。
- **根因：** Agent 执行和评分处于同一个异常捕获边界。
- **方案：** 分离执行异常与评分异常；Judge 最多重试 3 次，最终失败时保留真实 AgentRun，并使用确定性 Rubric 降级评分，同时记录 `judge_degraded`。
- **验证：** 坏 JSON 重试测试和 Judge 降级测试通过；全量评测 0 次 Judge 降级。
- **经验：** 观测和评价组件不能改变被观测对象的事实结果。

## 2026-08-23：用户纠正被误当成删除记忆

- **现象：** “以后改为 Python”可能触发 `forget_memory`，旧记忆被直接删除，无法保留纠错关系。
- **根因：** 隐私删除与偏好纠正共用模糊意图边界。
- **方案：** `forget_memory` 只处理明确的忘记、删除和隐私擦除；“改为、取消旧规则”等表达统一交给后台语义抽取与 supersede 治理。
- **验证：** 工具边界测试与记忆版本链测试通过。
- **经验：** 删除是不可逆隐私操作，纠正是可审计版本更新，两者必须使用不同链路。

## 2026-08-23：缺少 fixture 导致通过率含义失真

- **现象：** 早期结果为 30/54，24 个依赖前置状态的用例实际没有触发对应能力。
- **根因：** 评测只有执行和断言，没有 case setup/teardown。
- **方案：** 建立 `prepare → AgentLoop → observe → cleanup` 生命周期，补齐旧记忆、工具失败、Checkpoint 和长上下文四类 fixture。
- **验证：** 24 个 fixture 用例均通过真实持久化与轨迹检查；完整回归 hard gate 为 54/54。
- **经验：** 没有构造真实前置条件的测试，只能衡量评测基础设施完成度，不能衡量产品能力。

## 2026-08-23：循环保护只存在于测试，生产 Agent 可重复失控

- **现象：** 测试通过了重复工具调用拦截，但生产启动只注册权限 Hook；SubAgent、Workflow 和主动链路也各自使用不一致的轮数、超时与结果上限。
- **根因：** 防护依赖测试注入的内存 Hook，既未接入统一执行内核，也不会随 LangGraph Checkpoint 持久化。
- **方案：** 在现有执行内核加入可序列化 ExecutionGuard，统一限制重复/振荡、无进展、工具次数、模型与工具超时、单次/单轮/单任务结果预算；主循环将守卫状态写入 Checkpoint，子任务与主动链路复用同一判定机制。
- **验证：** 补齐重复只读调用、重复副作用、连续失败禁用、确定性截断、工具超时和旧式错误归一测试，并移除测试专用 LoopGuard。
- **经验：** 生产安全能力必须位于真实执行路径并可恢复；只存在于测试夹具中的保护等于没有上线。

## 2026-08-23：Workflow 静态 DAG 无法适应执行中产生的新证据

- **现象：** Workflow 创建时必须一次生成完整步骤 DAG；执行到一半发现原方案不可行时，只能重试、取消或重建整个任务。
- **根因：** 持久化层只支持创建和执行，没有对未完成步骤进行版本化重规划的能力，也缺少并发修改校验。
- **方案：** Workflow 只保留少量粗粒度阶段；新增带 `revision` 校验的 `replan`，仅替换未执行步骤，保留已完成结果和事件历史；若新计划扩大副作用或权限范围，则重新申请审批。
- **验证：** 覆盖已完成步骤保留、未完成尾部替换、过期 revision 拒绝和新增副作用重新审批；相关 Workflow 回归测试通过。
- **经验：** 长任务计划应当“状态持久、计划可变”，Checkpoint 保存事实进度，Planner 只负责调整尚未发生的未来。

## 2026-08-23：Fork SubAgent 重启后只能从整步开头重跑

- **现象：** SubAgent 进程中断后仍可找到 Workflow 和 Artifact，但内部 ReAct 位置、消息状态与工具轨迹丢失，恢复时会重复执行整个步骤。
- **根因：** Fork 使用一次性实例和内存 Checkpoint，没有稳定执行 ID，也没有进程级持久化 Checkpointer。
- **方案：** 使用 Workflow 步骤 ID 派生稳定 `execution_id`，让不同 SubAgent 实例共享独立的 SQLite Checkpointer；重启后按同一 ID 恢复尚未完成的 LangGraph 节点。
- **验证：** 测试先中断首个实例，再创建新实例使用相同 execution ID，成功从 SQLite Checkpoint 继续并获得最终结果。
- **经验：** Agent 与 SubAgent 可以共用同一执行内核，但必须隔离状态命名空间；可恢复性取决于稳定身份和持久状态，而不是对象是否仍在内存中。

## 2026-08-23：工具参数解析异常绕过 ReAct 自修复

- **现象：** 模型为 `task_create` 等工具生成多余或畸形 JSON 时，Provider 适配层直接抛出 `JSONDecodeError`，Agent 看不到原因，也没有机会修正参数后重试。
- **根因：** 解析异常发生在工具调用标准化之前，没有被转换为执行图可观察的模型反馈。
- **方案：** 将异常归一为 `ToolArgumentsDecodeError`，程序固定返回工具名、错误位置、明确原因和安全截断后的参数预览；反馈进入同一 ReAct 循环，最多允许两次修复，合法解析前不执行工具。
- **验证：** 覆盖尾随 JSON、非对象顶层参数、错误反馈可见性和模型修正后成功调用；Provider 与 Reasoner 回归测试通过。
- **经验：** 可修复的协议错误不应终止执行；程序负责提供确定性诊断，模型负责基于诊断重新生成合法动作。

## 2026-08-23：异常短回复被误判为正常完成

- **现象：** 模型只返回“我先看看……”等未完成短句且没有工具调用时，执行图直接结束并标记 `completed`。
- **根因：** 原终止条件只判断“没有 `tool_calls`”，丢失了 Provider 的 `finish_reason`，也没有检查未闭合结构和承诺执行却无动作等完成性信号。
- **方案：** 全链路保留 `finish_reason`；组合异常结束原因、未闭合代码块/结构和“承诺动作但无工具轨迹”识别疑似截断，将原回复与固定纠错提示回送同一 ReAct 循环，最多续跑两次。
- **验证：** 覆盖短回复续跑、补发工具调用和正常简短回答不误拦截；Reasoner 回归测试通过。
- **经验：** ReAct 的结束条件不能等同于“本轮没有工具”；系统应判断语义动作是否闭合，同时为模型保留有限的自愈机会。

## 2026-08-23：Windows Skill 复制降级触发路径长度上限

- **现象：** 无符号链接权限时，插件 Skill 会降级为目录复制；长逻辑名叠加完整 UUID 后使嵌套脚本路径超过 Windows 路径上限，最终同步失败。
- **根因：** 临时目录重复拼接长逻辑名和完整随机标识，没有为 Skill 内部的深层资源预留路径预算。
- **方案：** 临时复制目录改用固定短前缀和短随机 ID；最终受管目录名、指纹和所有权标记保持不变，避免影响查找与清理语义。
- **验证：** 原失败插件可在复制降级路径完成同步；插件 Skill 物化与全量后端回归测试通过。
- **经验：** Windows 上的临时路径也是资源预算；目录结构越深，基础路径和随机命名越应保持短且与业务标识解耦。

## 2026-08-23：统一工具超时误杀长时间 Shell 任务

- **现象：** `codex-delegate` 按设计使用 `shell(auto_promote=false)` 同步等待，但 Shell 被统一识别为副作用工具，30 秒后被外层取消；模型、SubAgent 和 Workflow 的较短上限还会二次中断本可完成的长任务。
- **根因：** 执行保护只按风险等级分配超时，没有区分普通工具、明确声明的阻塞任务和整个 Agent 生命周期；各层预算也没有满足外层大于内层的嵌套关系。
- **方案：** 模型调用放宽到 180 秒、普通工具 300 秒、阻塞 Shell 3600 秒，AgentLoop 使用 10 分钟软限制和 65 分钟硬限制，SubAgent、Workflow 单步依次为 65 和 70 分钟；`process_output` 的 30 秒仅用于轮询进度。超时与收敛判定解耦，继续通过重复调用/副作用去重、A-B 振荡、连续失败与无进展、单轮调用量和上下文预算防止失控，并将守卫计数写入 Checkpoint。
- **验证：** 覆盖阻塞 Shell 默认预算、显式短超时优先、自动转后台、重复/振荡拦截和中断恢复；相关超时组合回归 98/98 通过，当次全量测试 1422 项通过，重启后新配置生效。
- **经验：** 长时间运行不等于死循环；多层时限应按调用层级递增，是否终止应主要依据重复动作和有效状态变化，而不是单一短超时。

## 2026-08-23：历史渠道信息污染当前会话并导致文件无法交付

- **现象：** 用户明明在网页聊天，模型却受旧上下文影响认为当前在 QQ；网页和 QQ 生成文件后只返回本机路径或口头声称已发送，用户实际拿不到产物。
- **根因：** Prompt 缺少本轮真实 `channel/chat_id` 的高优先级运行时边界；生成文件、出站消息、网页下载和 QQ 富媒体上传之间也没有统一的 Artifact 交付契约。
- **方案：** 每轮强制注入不可被历史覆盖的真实渠道和会话 ID；从工具轨迹识别工作区内新生成的 Artifact，并统一通过 `message_push(channel, chat_id, file)` 回送当前会话。Dashboard 补齐文件登记、附件事件和下载接口，QQ 接入“预上传—分片上传—合并—富媒体消息”链路并限制单文件 200MB。
- **验证：** 真实 Dashboard 回合正确识别 `channel=dashboard`，附件可点击下载且内容一致；QQ 上传协议通过模拟 API 测试且未向真实账号发送测试消息；相关测试 91/91 通过，前端构建、TypeScript、ESLint 与 Ruff 均通过。
- **经验：** 渠道身份必须来自可信运行时元数据，不能由模型从历史对话猜测；文件只有在产生可下载附件或渠道上传成功回执后才算完成交付，本机路径不属于用户可用结果。

## 2026-08-24：历史实现与生成产物长期滞留主仓

- **现象：** 已退出运行链路的插件面板编译器、兼容模块和旧调试场景仍与现行代码并存，根目录及源码目录还积累了日志、缓存、旧数据库和大量评测结果。
- **根因：** 功能迁移时只增加新链路，没有同步删除旧入口、旧测试与旧依赖；可再生运行数据也没有严格落入工作区或忽略目录。
- **方案：** 从 `main.py`、Bootstrap 和 React 入口反向追踪可达性，整体删除未注册的旧插件前端链路、完全不可达模块及其专属测试；运行数据移出源码树，收紧 Python/Node 直接依赖，并将现行目录边界写入架构文档。
- **验证：** 以静态引用检查、架构边界测试、全量 Pytest、前端 TypeScript/ESLint/生产构建和真实服务启动共同验收；完整清单见《项目级代码审计（2026-08-24）》。
- **经验：** 删除旧方案必须以“入口不可达 + 没有外部契约 + 专属测试同步退出”为判据；历史测试不能成为废实现继续存在的理由。

## 2026-08-24：弱类型掩盖长期记忆接口接错层

- **现象：** 全仓静态检查存在 37 个硬错误；其中 AgentLoop 把 Markdown Store 传给需要完整长期记忆能力的 ContextBuilder，正常启动未必立刻报错，但检索到该分支时可能缺少 `read_long_term/get_memory_context`。
- **根因：** Bootstrap、插件和领域层长期依赖 `Any/getattr` 拼接接口，插件目录还未纳入 Pyright，导致“对象存在”被误当成“对象实现所需契约”。
- **方案：** ContextBuilder 改接 `MemoryRuntime.profile`；为 Markdown、MCP 安装和模型供应商建立最小 Protocol，收窄动态载荷并删除无消费方的回调参数；把插件目录、Ruff 和 Pyright 加入 CI。
- **验证：** Pyright 从 37 error 降至 0，插件单独检查从 4 error 降至 0；相关链路测试 158/158、全量后端回归 1424/1424 通过。
- **经验：** 类型检查不是注释美化，而是组合根的接线测试；跨层对象应依赖最小能力契约，不能用宽泛实现类或 `Any` 掩盖边界错误。

## 2026-08-24：旧测试反向供养无调用方的生产代码

- **现象：** Shell 旧执行器、工具集兼容包装、记忆规则冲突函数等代码在测试中有覆盖率，但 `main.py`、Bootstrap、动态插件入口和离线脚本均不会调用；测试文件仍以 `p1/p2/baseline` 等迁移阶段命名。
- **根因：** 过去按“有测试就保留”判断代码价值，没有把生产入口引用与测试引用分开统计；重构阶段的临时 API 和命名因此被长期固化。
- **方案：** 以生产入口可达性、动态注册契约和离线工具入口三类证据复核符号；删除只被旧测试调用的生产函数及对应墓碑测试，并把保留测试重命名为推理器、上下文、执行内核、回合提交和记忆检索等业务域名称。
- **验证：** 清理后的受影响模块定向回归 180/180 通过，Ruff 通过，Pyright 保持 0 error；完整结果记录在《项目级代码审计（2026-08-24）》第三阶段。
- **经验：** 测试只能证明实现符合断言，不能证明实现仍被产品使用；审计必须分别检查生产可达性与测试覆盖率，禁止让墓碑测试成为废 API 的续命理由。

## 2026-08-24：领域层反向依赖运行时并形成隐式循环

- **现象：** `core` 领域包直接引用 Agent、基础设施和会话实现，工具搜索、Prompt 组装、Lifecycle 与 Bootstrap 又存在 4 组循环依赖；配置入口还产生 375 个弱类型告警。
- **根因：** 迁移时按调用方便放置实现类与装配函数，共享数据模型依附在某一侧模块中；TOML 原始对象也未经边界解码直接流入配置构造。
- **方案：** 将存储实现、语义批次和插件装配移回各自层，抽出 Agent 执行端口、Markdown 端口、调度模型和工具目录模型；配置值通过显式列表/数值转换进入强类型模型，并新增领域依赖和循环依赖门禁。
- **验证：** `core` 对运行层引用清零，生产模块循环依赖从 4 组降为 0，`agent/config.py` Pyright 告警从 375 降为 0；核心链路定向回归 168/168 通过。
- **经验：** 共享契约必须位于依赖双方都能单向访问的稳定层；组合根只负责装配，原始配置和动态载荷必须在入口完成解码，不能把 `Any` 与循环引用留给运行时消化。

## 2026-08-24：供应商响应和记忆命中以无类型字典贯穿主链

- **现象：** Provider 与记忆召回器分别积累 169 和 134 个弱类型告警；上游一旦缺少 `choices/function`，或记忆 `extra_json/score` 类型异常，错误会在 AgentLoop 或 Prompt 注入阶段才暴露。
- **根因：** 外部 SDK 对象、SQLite 行和召回字典没有在各自适配边界完成解码，多厂商差异与内部业务结构混在同一批 `Any/getattr` 中。
- **方案：** Provider 统一解码 Completion、usage、流式增量和工具调用；记忆链建立 `MemoryHit` 合同，并在注入前归一嵌套元数据、分数、步骤和来源字段。
- **验证：** 两个核心文件 Pyright 均达到 0 error/0 warning；补充畸形 Provider 响应和畸形记忆命中的隔离测试，相关回归全部通过。
- **经验：** 动态数据可以存在于系统边缘，但必须在进入执行与推理链之前变成可验证合同；类型异常应就地失败或降级，不能延迟污染主上下文。

## 2026-08-24：Dashboard 所有功能页被同步装入首屏

- **现象：** 用户只进入聊天页，浏览器仍下载记忆图谱、MCP、主动协助等全部管理页面；生产入口 JS 达 592KB，并持续触发 Vite 大包警告。
- **根因：** `main.tsx` 从功能聚合文件同步导入全部页面，视图切换只控制渲染，不构成代码加载边界；构建流程也没有包体回退门禁。
- **方案：** 各功能页改为 `React.lazy` 按视图加载，统一使用 `Suspense` 加载态，删除无调用方的同步聚合入口；构建后校验入口和最大 JS 分包均不超过 300KB。

- **质量边界：** 最终金额和推荐正确不代表理由都正确；10 次会务回答中 7 次误把提前 24 小时取消看作不满足提前 48 小时取消。另一次使用资料 ID 代替中文名，被字段检查判失败但语义正确。保留原始评分，再单独记录人工复核，不混为一个能力通过率。
- **验证：** 共 18 次任务、70 次真实模型调用、247,710 tokens；模型固定 deepseek-v4-pro-0813/high。隔离 SQLite、固定只读模拟资料、无工具人为等待，未触碰个人记忆或发送渠道；结果在 eval/reports/delegation-live-20260906/REPORT.md，脚本为 eval/delegation_live_benchmark.py。没有声称真实网站/完整网页链路覆盖，也没有把累计 tokens 换算成未知账单金额。
- **经验：** 多 Agent 要以阶段边界、实际证据复用和端到端完成时间评估；增加子执行器不是优化本身。数值与时序约束需要专项用例，字段命名错误和语义错误应分开衡量；两次试验不能外推稳定提速百分比。

## 2026-09-08：Drift 通知与主动打扰链路分叉

- **现象：** Drift 的 `message_push` 直接调用专用发送回调，绕过普通主动提醒的去重、免打扰和取消复核；发送前就记录为已联系，失败或结果未知时状态不准确。
- **根因：** 探索分支把“生成通知候选”和“渠道发送回执”混成一个动作，维护了第二套发送收尾逻辑。
- **方案：** Drift 只暂存 `notification draft`（文字/媒体），结束后转换为统一 `Resolve → Deliver` 输入；统一出口负责来源校验、消息去重、免打扰、取消、投递状态和 quota。新增 `accepted / unconfirmed / not_requested` 状态，界面不再把未确认结果显示为“已联系”。
- **验证：** 隔离模型和测试渠道覆盖文字/图片、重复候选、排队后免打扰、停止服务、发送异常和旧数据库迁移；主动模块及新增回归共 365 项通过，新增端到端统一链路用例通过，Ruff、Pyright（0 errors）、TypeScript、ESLint、Vite 构建和 bundle 检查通过。未向真实渠道发送消息。
- **经验：** 主动探索可以与主动提醒共享同一执行内核；候选生成、准入决策、发送和回执必须是不同状态，模型不能直接声明“已发送”。

## 2026-09-09：真实评测证据与偏好重复抽取

- 现象：恢复场景的备用工具只返回“fallback completed”，模型无法交付配置、搜索结果、网页正文或附件内容；评测只看 hard gate 时仍显示 100%。同一条用户偏好还可能同时生成全局键和场景键。
- 根因：夹具没有绑定真实/明确的成功、空结果、数据缺失三态；运行器只读取文本和 trace 摘要，未保留退出原因、工具结果与 Judge 理由；语义模型候选与确定性兜底在写入前没有统一主体、槽位和范围。
- 方案：备用夹具返回结构化证据并区分三态；评测记录 `status/exit_reason`、完整工具轨迹和 Judge reasons，报告拆分执行完成、hard gate、质量达标和 Rubric 全通过；统一 `preference_slot + subject + scope` 去重，窄范围候选不再补写全局版本；当前用户原文增加明确标记，避免被上下文提醒误判为系统消息。
- 验证：定向测试 63 项通过；真实模型评测 memory 6/6 执行完成、Judge 质量 5/6，且每个场景仅新增一条偏好记录；recovery 8/8 执行完成、Judge 质量 7/8，8 个场景均返回可核验交付或明确不可用状态。质量未达标的 case 仍保留在报告中，不以 hard gate 通过替代质量结论。
- 经验：工具调用成功不等于任务完成；评测必须同时保留终态、证据和扣分理由。记忆去重必须在统一身份边界后进行，不能只按标签或文本相似度合并。

- 复测补充：渠道偏好定向复测由寒暄改为准确确认，Judge 由 0.2 到 1.0，仍只产生一条 `communication_channel`（scope=work）。恢复记忆原回复已经交付正确偏好，Judge 把“不应只汇报备用调用”误解为“不许说明恢复过程”而给 0.5；修改后的单例为 1.0，不能据此证明系统整体质量提升。没有最终同版本全量复测，不拼接最好单例结果。
- 回归边界（口径更正）：该次测试为 1536 passed、9 failed、2 deselected，另整体排除了 Workflow 通知测试模块，并非全量通过。通知模块独立复现 `WorkflowStore.notifications` 缺失；其余失败尚需逐项核对实际接口与测试预期，不能一律归为“旧测试”。定向 63 项通过不替代这些未闭环项。

## 2026-09-09：评测高通过率掩盖任务未完成

- 现象：工具出现过、内核正常返回，就可能得到高 hard-gate 通过率；单次最好结果、受控夹具和模型 Judge 误判混入“系统完成率”。
- 根因：缺少独立目标/交付验收，软质量没有接入退出门禁；字符串与工具名检查过浅；单轮用例和共享测试状态无法代表长期个人助手。
- 方案：新增证据驱动 acceptance、类型化事实/工具参数与返回校验、真实多轮和跨会话运行；每例每次独立 runtime，dev/holdout 隔离，3 次重复全部保留并聚合，默认质量门禁、版本指纹和 Judge 待人工校准集。
- 验证边界：真实模型样例走内核，不包含网页、真实外发渠道、进程崩溃恢复；生成文件落盘不当作发送成功；诚实受阻可以验收合格但目标完成数不增加。详细命令、指标和剩余产品闭环见 `eval/README.md`。
- 经验：评测结果必须说明分母、执行层级和证据来源。既评 Agent，也检查评分器；不能用“换口径后高分”代替同条件能力提升。
