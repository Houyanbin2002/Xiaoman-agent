# 个人助手 Harness 分阶段改进计划

日期：2026-09-05。以当前主 AgentLoop / Fork / Workflow、记忆、调度与交付链为基础完善，不新增平行执行框架，不以简历指标作为验收目标。

## 验收原则

- 完成必须有证据：回复“已完成”不等于文件可下载、提醒已保存或消息已送达。
- 保护不能误伤：区分重复请求、重复结果、失败、等待和真实进展；保留有限资源预算与取消能力。
- 中断可以解释：恢复任务不能重复产生副作用；无法确认是否送达时，必须报告不确定性。
- 长期与短期分开：稳定偏好、当前活动、待履行承诺分别治理，完成/取消必须影响后续召回与通知。
- 数据诚实：确定性回归、模拟服务、真实模型与真实渠道分别报告，不混成“产品通过率”。

## 第一阶段现状与范围

已核实的问题：

1. `before_tool_batch` 只按连续参数签名拦截，未检查结果是否发生变化；读取不断更新的文件可能第三次就被终止。
2. 无进展判断只比较结果，不比较操作；不同文件都返回相同 OK 可能触发误停。
3. 重复副作用按整个批次签名判断，混入新的查询就能绕过；`process_stop` 还与只读轮询共享豁免。
4. 结果摘要只取前 8,000 字符，尾部发生变化不能被识别。
5. 软超时提示要求转 Workflow，禁用工具提示误称“后台任务”，子 Agent 反思提示禁止报告失败原因；均与实际执行边界或如实交付不一致。
6. 一次性 SubAgent 重建工具表时没有传入风险元数据，写文件和 Shell 也被默认标为只读。现改为由 research/scripting/general 配置显式传递；未声明的工具保守按有副作用处理，避免工具表重建削弱保护。

1A 当时只修复保护正确性，保留原调用次数、时间、上下文和结果上限；当时 `max_tool_calls=12` 是**一次执行累计调用数**，不是每个模型回合 12 次。以下 1B 记录替代旧预算配置，仍不能宣称任意长任务均可连续执行。

副作用签名保护只覆盖同一次执行和其 Checkpoint 延续，不等价于渠道层幂等：进程在外部发送成功、落 Checkpoint 前崩溃的窗口仍需阶段 2 的交付记录与回执机制。

结果变化也不等价于任务取得实质进展：本批只消除确定性误判，不引入额外 LLM 判定。仅时间戳变化、重复但已授权的操作、后台进程长时间无输出、工具明确拒绝与执行结果未知的区别，均需在后续预算/副作用治理中进一步区分。旧 Checkpoint 没有逐调用指纹时仍保留原批次保护，不能追溯补出从未保存的信息。

## 1B 修复记录：长任务预算、完成合同与进程归属

2026-09-05，本轮沿用原 LangGraph、Shell 注册表与 Workflow Store，无新建执行循环或数据库。

核实并修复：

1. **未完成被记为成功：** 主循环通过 `TurnRunResult → OutboundMessage.metadata` 传递退出原因；Workflow 调用显式要求 `require_completed`。SubAgent 同样检查退出原因，预算耗尽、强制收尾、空结果和超时均不能作为正常结果提交。复用 `FAILED/BLOCKED`，保留错误与已有部分结果，不自动重试、不启动依赖步骤；需要用户检查后手动重试或调整计划。
2. **多层预算叠加误停：** 普通操作默认 48 次、子执行器 24 次；`process_output` 独立 120 次、`process_stop` 独立 4 次。有效 JSON 返回、任务 ID 匹配且状态为 `running` 的纯轮询轮不消耗普通模型迭代额度；错误、未知任务和已结束结果仍消耗迭代额度。计数随 Checkpoint 保存。示例及当前本地配置将主模型迭代额度由 16 调至 32，子执行器保留 10。
3. **Shell 内外超时矛盾：** 普通/同步 Shell 统一默认及最大 3600 秒，自动转后台继续继承该期限，不再暗含 60/600 秒限制或宣称可阻塞 6 小时。普通后台任务再取所属执行剩余时间与配置预算的较小值。整轮 3900 秒上限由异步 deadline 实际约束，模型和工具调用也取剩余预算，不能在临近到期时再获得完整一小时。
4. **摘要水位无法到达：** 原 200K 摘要触发高于 160K 硬保护。默认硬保护调整为 256K，保留原 200K 分代会话摘要；旧配置则自动将会话摘要水位提前到硬保护之前。仍沿用原多轮历史摘要与 Cache Breakpoint 的分工，不宣称单轮工具链拥有新增的任意长度摘要能力。
5. **累计输出误当实际上下文：** 6 万字符改为软提醒，达到后后续工具结果收紧至最多 3000 字符；继续保留单结果/单批限长、Cache 压缩和当前模型视图的 token 硬保护。有进展任务不再只因过去已处理过较多文本而结束。
6. **后台进程脱离生命周期：** 在现有 Shell 注册表附加 execution owner 和 `keep_alive`。正常结束、预算退出及取消均清理该执行未结束的临时进程；若最终回复时仍有临时进程，返回 `background_incomplete`，不得冒充完成。仅 `run_in_background=true, keep_alive=true` 的长期服务跨回合保留，另一个回合与旧版无 owner 的进程不被误杀。

## 2A 修复记录：撤销生效、保守恢复与交付状态

2026-09-05，沿用 Scheduler 的 JobStore、Workflow 的 SQLite、现有 ChatLane 与 MessagePushTool，不增加独立调度框架。

### 已确认并修复

1. **撤销只删配置、旧执行仍发消息。** Scheduler 现在跟踪正在执行的 asyncio task，取消/按名取消/替换任务会撤销旧执行；模型返回后、推送前以及 ChatLane 排队结束后再次验证任务对象身份。即使 Provider 吞掉取消并返回结果，也不能把旧结果发出或覆盖新版本。服务退出会取消并等待子执行清理。
2. **定时任务在开始前仍以 pending 落盘。** 现在先保存 `running/last_attempt_at` 再执行；启动恢复发现 `running` 时保留为禁用的 `interrupted`，展示结果未知，需要核对后编辑重新启用。正常尚未执行任务仍沿用原 misfire 规则。SOFT/WATCH 调用增加 `require_completed=True`，预算收尾不再直接当作提醒结果成功发送。
3. **Workflow 中断重试不区分副作用。** Store 默认不自动重放，Runtime 根据真实工具风险/执行器 profile 明确允许只读步骤自动恢复；写入、命令执行及未知工具需要检查后通过原 retry/replan 入口继续。通用步骤异常也采用同一重放策略；已完成步骤仍保留。恢复事件的中断数量改为按各 Workflow 分别计算。
4. **通知结果靠字符串猜。** Workflow 改用 `PushDeliveryResult.success`，不支持文本、无渠道目标或发送异常均不能标记已通知。同进程的等待/结束通知串行领取检查，避免并发扫描重复发出。清除 wake 信号移到扫描开始，通知 await 期间的新建/完成信号不再丢失。
5. **附件部分失败丢证据。** MessagePushTool 在发任何部分前检查整包渠道能力及本地附件存在性；记录 `sent_parts/unknown_parts`，明确不要重复发送已成功的部分。通过工具接口调用时失败采用既有错误合同，实际 ToolExecutor 轨迹标 error，不再把渠道失败作为成功工具证据。
